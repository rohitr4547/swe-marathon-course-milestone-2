# E.3: IRC bridging

Rule group: **E3**.
Check: `bash /spec/e/checks/check_e_3.sh`. The rule numbers below match its output.

Do not start this step until `check_e_2.sh` prints `RESULT: 5 passed, 0 failed`.

This step also holds the IRC part of surviving a killed node (E3.4): the IRC gateway lives in
Spec E, so its failover rule does too.

## Uses

| Function | Used here for |
|---|---|
| `create_message(user, channel_id, body)` | `PRIVMSG` commits a normal message: same validation, same event |
| `head_event_id(...)`, `events_after(...)` | Delivering web messages to IRC by polling (architecture rule 5) |

## Adds

| Function | What it does |
|---|---|
| `irc.py: deliver(conn)` | A separate task per connection, started by `handle` after registration and cancelled when it ends: every 0.05 s, sends new `message.created` / `message.reply` events of joined channels |

## Rules

### E3. IRC bridging

E3.1 **IRC to web.** `PRIVMSG #slug/name :<text>` on a joined channel creates a message by the
token's user through `create_message`: it shows in `GET /api/channels/{id}/messages` on every node
and reaches WebSocket subscribers as `message.created` with the next `event_id`.

E3.2 **Web to IRC.** A message posted on the web to a joined channel reaches the IRC client as
`:<author-username>!<author-username>@huddle PRIVMSG #slug/name :<body>`. A message an IRC
connection sent is never echoed back to that connection.

E3.3 **One sequence.** IRC and web writes to the same channel, interleaved, share one dense
`event_id` sequence.

E3.4 **Survives a killed node.** With the HTTP node on `8001` killed, a web post through `8002`
still reaches the IRC client, and an IRC `PRIVMSG` is still stored and readable through `8000`.

Every request must answer within 5 seconds.
