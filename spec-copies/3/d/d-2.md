# D.2: A killed Redis

Rule group: **D2**.
Check: `bash /spec/d/checks/check_d_2.sh`. The rule numbers below match its output.

Do not start this step until `check_d_1.sh` prints `RESULT: 8 passed, 0 failed`.

## Uses

| Function | Used here for |
|---|---|
| `start.sh` (architecture) | Its Redis loop respawns `redis-server` |
| Architecture rule 5 | Delivery reads the database, so fan-out never depends on Redis |

## Adds

Nothing: keep Redis out of every request path. If you also publish to Redis, wrap each publish in
`try/except` with a short timeout so a dead Redis never fails or delays a write.

## Rules

### D2. A killed Redis

D2.1 **Writes keep working.** After `SIGKILL` of `redis-server`, posts through each of `8000`,
`8001` and `8002` return `201`, all within 5 seconds.

D2.2 **Fan-out keeps working.** WebSocket subscribers on `8000` and `8002` receive all of those
posts during the outage, with `event_id`s still dense from the head they subscribed at.

D2.3 **Redis comes back.** `start.sh` restarts Redis (it answers `PING` again) within 10 seconds,
and posts after that still reach subscribers on other nodes with the next `event_id`.

Every request must answer within 5 seconds.
