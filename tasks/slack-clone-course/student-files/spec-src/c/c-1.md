# C.1: Conventions and reactions

Rule groups: **C0** (API conventions on Spec C routes) and **C1** (reactions).
Check: `bash /spec/c/checks/check_c_1.sh` (append `C0` or `C1` to run one group). The rule numbers
below match its output.

Builds on: register, workspaces, channels, join, messages and WebSocket subscribe (the basics named
in `/spec/README.md`). Read `/spec/common/architecture.md` before writing code.

## Uses

| Function | Used here for |
|---|---|
| `require_user(request)`, `read_json(request)`, `json_error(...)`, `tx()` | Auth, body parsing, errors, transactions |
| `get_channel(id)`, `can_read_channel(user_id, channel)`, `require_writable(channel)` | `404`, `403`, `423` |

| `emit_event(c, channel_id, kind, payload)` | `reaction.added` and `reaction.removed` |

|---|---|

## Rules

### C0. Conventions on Spec C routes

C0.1 **401 comes first.** Each of these returns `401` with no `Authorization` header, and with a
made-up token, before anything checks whether the id exists: `POST /api/messages/{id}/reactions`,
`DELETE /api/messages/{id}/reactions/{emoji}`, `POST /api/dms`, `POST /api/files`,
`GET /api/files/{id}`, `GET /api/files/{id}/download`, `GET` and `POST /api/workspaces/{slug}/groups`,
`PATCH` and `DELETE /api/workspaces/{slug}/groups/{handle}`, `GET /api/users/{id}`,
`PATCH /api/users/me`.

C0.2 **404 for unknown ids.** With a valid token, an unknown message id (reactions), file id
(`GET /api/files/{id}` and its `/download`), user id (`GET /api/users/{id}`, `POST /api/dms`) or
workspace slug (`GET /api/workspaces/{slug}/groups`) returns `404`.

### C1. Reactions

C1.1 **First reaction.** `POST /api/messages/{id}/reactions` with `{emoji}` returns `200` (not
`201`, even the first time) and `{reactions: [{emoji, count, user_ids}, ...]}`.

C1.2 **Idempotent per user and emoji.** The same user adding the same emoji again changes nothing.
A second user adding it makes `count` 2, with `user_ids` in the order users reacted.

C1.3 **Any emoji.** Unicode emojis such as `🎉` work in the POST body and, URL-encoded, as the
`{emoji}` path segment of DELETE. The list keeps emojis in the order they were first added.

C1.4 **Remove.** `DELETE /api/messages/{id}/reactions/{emoji}` removes only the caller's reaction
and returns `200` and `{reactions}`. Removing a reaction the caller does not have returns `200` and
changes nothing. An emoji with no users left is dropped from the list.

C1.5 **In message objects.** Every `MessageObj` (for example in
`GET /api/channels/{id}/messages`, on any node) carries the same `reactions` list.

C1.6 **Events.** Adding a reaction emits one `reaction.added` and removing one emits one
`reaction.removed`, each with `message_id`, `emoji` and `user_id`, each advancing the channel's
`event_id` by exactly 1. A repeated add or a removal of an absent reaction emits nothing.

C1.7 **Validation and access.** An empty, non-string or missing `emoji` returns `400`. A user who
cannot read the channel (for example a non-member of a private channel) gets `403`. Reacting in an
archived channel returns `423`.

Every request must answer within 5 seconds.
