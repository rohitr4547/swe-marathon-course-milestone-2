# E.1: Conventions and message edits

Rule groups: **E0** (API conventions on the edit routes) and **E1** (editing and deleting messages).
Check: `bash /spec/e/checks/check_e_1.sh` (append `E0` or `E1` to run one group). The rule numbers
below match its output.

Builds on: register, workspaces, channels, join, messages, threads (`parent_id`, replies) and
WebSocket subscribe (the basics named in `/spec/README.md`). Read `/spec/common/architecture.md`
before writing code.

## Rules

### E0. Conventions on the edit routes

E0.1 **401 comes first.** `PATCH /api/messages/{id}` and `DELETE /api/messages/{id}` return `401`
with no `Authorization` header and with a made-up token, before checking the id.

E0.2 **404.** With a valid token, both return `404` for an unknown message id.

### E1. Editing and deleting messages

E1.1 **Edit.** `PATCH /api/messages/{id}` with `{body}` by the author returns `200` and `{message}`
with the new `body` and `edited_at` set (UTC, ending in `Z`). Every node's history shows the edit.

E1.2 **Edit rules.** Only the author may edit: anyone else, the workspace owner included, gets
`403`. A body that is empty, only spaces, `null`, not a string or missing returns `400`. A request
body that is not valid JSON returns `400` on every route.

E1.3 **Delete.** `DELETE /api/messages/{id}` by the author or the workspace owner returns `200` and
`{"deleted": true}`; deleting it again also returns `200`. Anyone else gets `403`.

E1.4 **Deleted is final.** Editing a deleted message returns `409`.

E1.5 **Gone from lists.** A deleted message disappears from channel history, from its thread's
replies and from search; a parent's `reply_count` counts only replies that are not deleted.
Reactions on a deleted message no longer count anywhere.

E1.6 **Mentions follow the edit.** An edit resolves `mentions` again from the new body: adding
`@user` adds their id, removing it empties the list.

E1.7 **Events.** An edit emits one `message.updated` carrying the edited `message`; the first
delete emits one `message.deleted` carrying `message_id`; a repeat delete emits nothing. Each
event advances the channel's `event_id` by exactly 1.

Every request must answer within 5 seconds.
