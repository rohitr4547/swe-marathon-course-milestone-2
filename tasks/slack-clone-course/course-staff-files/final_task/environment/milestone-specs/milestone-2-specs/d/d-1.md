# D.1: Baseline and a killed HTTP node

Rule groups: **D0** (cluster baseline) and **D1** (a killed HTTP node).
Check: `bash /spec/d/checks/check_d_1.sh` (append `D0` or `D1` to run one group). The rule numbers
below match its output.

Builds on: register, workspaces, channels, join, messages and WebSocket subscribe and resume (the
basics named in `/spec/README.md`). Read `/spec/common/architecture.md` before writing code: its
`start.sh` and design rules 1 to 5 are what make these rules pass.

## Uses

| Function | Used here for |
|---|---|
| `start.sh` (architecture) | Respawning a killed node and Redis |
| `emit_event(...)`, `events_after(...)`, `head_event_id(...)` | Dense events that every node can replay from the database |
| `server.py: ws_handler(request)` | Subscribe, resume and live delivery |

## Adds

Nothing new beyond the architecture: these rules prove the cluster survives failures. If one
fails, fix the shared design (one database, events in the database, delivery by polling,
respawn loops), not a special case.

## Rules

### D0. Cluster baseline

D0.1 **Health on every node.** `GET /api/health` on `8000`, `8001` and `8002` returns `200` and
`{"status": "ok", "node_id": 0}`, `1` and `2` respectively.

D0.2 **WebSocket rejects a bad token.** A handshake to `/api/ws?token=<made-up token>` gets `401`
and is never upgraded (no `101`).

D0.3 **Boot files and Redis.** `127.0.0.1:6379` answers `PING` with `+PONG`; `/app/start.sh` is
executable; `/app/requirements.txt` exists.

### D1. A killed HTTP node

D1.1 **The others keep serving.** After `SIGKILL` of the process listening on `8001`, ports `8000`
and `8002` keep answering `/api/health`, history reads (`200`) and posts (`201`).

D1.2 **Live delivery continues.** A WebSocket subscriber on `8002` receives every post made
through `8000` and `8002` during the outage, with consecutive `event_id`s.

D1.3 **Replay after reconnecting.** A WebSocket connected to the killed node is closed by the
kill. Reconnecting to `8000` and sending `resume` with the last `event_id` it saw replays every
missed event in order, then `resumed`.

D1.4 **The node comes back.** `8001` answers `/api/health` again with `node_id` `1` within 15
seconds (the contract allows 60; the `start.sh` loop needs about 1), shows the same history as
the other nodes, and reports the same `head_event_id` on subscribe.

D1.5 **Back in the cluster.** After it returns, a post through `8001` reaches a subscriber on
`8002` live with the next `event_id`.

Every request must answer within 5 seconds.
